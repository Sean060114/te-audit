# 基准字段语义校准：EDTA 结构法 LTR 元件

> 2026-11-23。本文是「建基准」的第 1 步：在建 A/B/C 三套参照集之前，先把
> `intact.gff3` 里每个字段的含义、坐标约定钉死。**语义没钉死之前，任何复算率
> 都是噪声。**

## 一、为什么必须先做这一步

第一次按直觉复算 `tsd=` 时，用了两种最自然的约定，命中率分别只有 **8.1%** 和
**23.8%**。看起来像"字段不可靠"，实际是**约定错了三处**：元件行混进了子特征行、
负链未取反向互补、`motif` 被当成连续 4 碱基搜。三处修正后，同一批数据的复算率
是 **99.0%**。

这就是本节存在的理由：**同一份数据，约定错时 8%，约定对时 99%**。先把约定写下来。

## 二、七条语义（据源码与实测确认）

源码：EDTA v2.2.2 `bin/make_gff3.pl`（tag `v2.2.2`，commit `911304b`）与
LTR_retriever `bin/make_gff3.pl`（master，v2.3.5 同期）。

| # | 语义 | 依据 |
|---|---|---|
| 1 | 坐标是 **1-based 闭区间** | `print GFF "$chr\t...\t$element_start\t$element_end"`，取值直接来自 pass.list 的 `lTSD`/`rTSD` 坐标 |
| 2 | `repeat_region` 的起止 = **5′TSD 第一个碱基 … 3′TSD 最后一个碱基**，TSD **含在**元件坐标内；仅当 `tsd=NA` 时退化为左右 LTR 起止 | `$element_start=(split /\s+/, $lTSD)[0]; $element_end=(split /\s+/, $rTSD)[1];` 及随后的 `if ($TSD eq "NA")` 分支 |
| 3 | `tsd=` 按**元件方向**书写：负链元件需反向互补后再与基因组比对 | 负链按元件方向输出，实测 217 条负链全部需 rc 才成立 |
| 4 | `motif=TGCA` 是**LTR 末端基序**，拆成「前 2 nt + 后 2 nt」，分别落在 5′LTR 起点与 3′LTR 终点，**不是**边界处连续的 4 个碱基 | `motif` 直接取自 pass.list 的 `motif:` 字段；约定正确后实测 98.8% 满足拆分规则 |
| 5 | 一个 LTR 元件在 `intact.gff3` 里占 **6 行**（`repeat_region` / `lTSD` / `lLTR` / `LTRRT` / `rLTR` / `rTSD`），**只有 `repeat_region` 行代表元件** | 420 元件 × 6 = 2,520 行，与文件实际行数吻合 |
| 6 | **两翼 LTR 都按基因组正向书写**，负链元件也不做反向互补；相似度直接比对两段（需先比对再算，不能逐位 hamming） | 实测负链元件 `lLTR`/`rLTR` 前 30 bp 完全相同；取 rc 后相似度从 0.93 掉到 0.23 |
| 7 | **`motif=` 与 `tsd=` 一样按元件方向书写**，负链元件要反向互补；且因为基因组小坐标端是负链元件的 **3′** 端，还要**交叉**：`rc(大端 LTR 末 2 nt) == motif[:2]`、`rc(小端 LTR 头 2 nt) == motif[2:]` | 10 条 motif 不一致里，**5 条负链按此约定立刻成立**；第 6 条（LTR 不 rc）与第 7 条（motif 要 rc）方向相反，同一脚本里必须分开处理 |

第 5 条是最容易踩的坑：按 `classification=LTR/*` 统计会得到 2,520，按元件统计是
**420**——两者相差 6 倍，而报告里此前出现的「420 条」正是元件数。

**第 6 条与第 7 条方向相反，这是本项目最容易连环出错的地方**：LTR 序列两翼**不**取
rc，而 `tsd=`、`motif=` 两个字段**要**取 rc。初版只处理了 tsd，没处理 motif，结果
motif 率停在 97.6%（410/420）——而且**看起来完全正常**：420 条里 406 条的正读与
rc 读同时成立（末端 2 nt 常相同或回文），把 5 条负链元件的错读整个掩盖住了。修完
是 98.8%（415/420）。

**教训：一个 97% 的数字，可能把 100% 的某类缺陷藏得严严实实。** 判据要通过，就得
拿"预期会失败的那一小组"去反查，而不是看总体通过率。

## 三、复算结果（Chr1+Chr12，双条运行）

命令见第五节。输出：

| 指标 | 结果 |
|---|---:|
| LTR 元件（`repeat_region` 行） | **420** |
| 5′ TSD 与序列完全一致 | **416 / 420（99.0%）** |
| 3′ TSD 与序列完全一致 | **420 / 420（100%）** |
| 两侧同时成立 | 416 / 420（99.0%） |
| 末端基序（motif 前 2 + 后 2，负链取 rc 并交叉） | **415 / 420（98.8%）** |
| 两翼 LTR 相似度 vs `ltr_identity`（\|差\| ≤ 0.01） | **399 / 420（95.0%）**，中位 \|差\| 0.0001 |
| `ltr_identity` 字段值（中位 / 最小） | 0.9927 / 0.9199 |

**结论：结构自证这一证据位，在这 420 条元件上成立。** 它不再依赖"EDTA 说它对"，
而是能被基因组序列独立重算。

**跨物种复核**（拟南芥 TAIR10 Chr1，同一脚本不改一行）：41 条元件，5′ TSD 95.1%、
3′ TSD 100%、motif 87.8%。motif 偏低的原因是部分元件的末端基序不是 `TGCA`
（存在 `TGTG…CACA` 一类），提示该检查应按 motif 字段本身而非固定 `TGCA` 判断——
本脚本已是这么做的，低值属真实分布，不是脚本缺陷。

## 四、5 条例外的性质：边界落在微卫星里

结构三项不全过的共 5 条（4 条 5′TSD + motif 同时失败，1 条只 motif 失败）：

| 位点 | 链 | TSD | motif | 末端 ±12 bp 内 TG/CA 的落点 |
|---|---|---|---|---|
| Chr1:19440230 | − | ATATA | TGCA | TG@+1，CA@−9/+5 |
| Chr1:34970456 | + | GAGAG | TGCA | TG@+4/+11，CA@−6/+3 |
| Chr12:4851235 | − | TATAT | TGCA | TG@+1/+4，CA@−9 |
| Chr12:4968252 | + | GGCGG | TGCA | TG@−6/+6，CA@−9/−6/+2 |
| Chr12:9998173 | + | TATAT | TGCA | TG@−5/+4/+7，CA@−9/−6 |

共同点是 **TSD 为 2 nt 交替重复**（ATATA / GAGAG / TATAT，4/5 条；第 5 条 GGCGG 是
3 nt 交替），motif 都写着最经典的 `TGCA`，但末端拿不到。而 TG/CA 在 ±12 bp 内的
落点**散在多个位置且不一致**，不是统一的 ±2 bp 偏移，所以**不能归因于"边界差几个
碱基"**。

合理的解释是：基因组这一段本身就是微卫星，**TSD 在重复区里有多个等效位置**，边界
在原理上不可唯一定位；LTR 末端同时被重复滑移占据，基序退化。这类元件的**坐标不可
复现**——同一个位置 ETH 换个参数就会挪 2–6 bp。

在基准里应当标注为「边界落在低复杂度区」，**既不算 EDTA 报错，也不能当 A 集**，
因为下游拿它做坐标级评测时无法判断对错。占 420 条的 1.2%。

## 五、未闭合项与已完成的版本核对

**1. `ltr_identity` 已可独立复算（原记"无法复算"，是判断错误）。**

原判断的理由是"复算需要左右 LTR 各自的起止坐标，而 `*.pass.list` 未随产物回传"。
**坐标一直在 `intact.gff3` 里**——每个元件有 `lLTR` / `rLTR` 两行（840 行 = 420×2），
只是此前没去读。不是数据缺失，是没找。

复算结果（`verify_ltr_structure.py`，定义 C）：

| 项 | 值 |
|---|---:|
| 有双翼坐标的元件 | 420 |
| 两侧 LTR 长度相等 | 184 / 420（等长中位 990 bp） |
| \|复算 − 字段\| 中位 | **0.0001** |
| \|差\| ≤ 0.01 | **399 / 420（95.0%）** |
| \|差\| ≤ 0.05 | 420 / 420（100%） |

**先说一个差点又踩的坑**：两侧 LTR 有 236/420 不等长，此时逐位 hamming 会整体错位
（差 3 bp 就能把 0.93 算成 0.63），必须先比对。而负链元件**不需要反向互补**——
`lLTR` 与 `rLTR` 都按基因组正向书写（实测前 30 bp 完全相同，取 rc 反而掉到 0.23）。
这与 TIR 侧相反（TIR 判反向重复要拿左翼比 rc(右翼)），是第 6 条语义。

**残差的性质**：三种常见定义（A `2M/(la+lb)`、B `M/对齐列`、C `1−错配/重叠`）在
0.01 内的命中率分别是 91.7% / 83.6% / 95.0%。**没有一种定义能解释全部**——个别元件
两种定义给出相反方向（`repeat_region_2`：A 给 0.9326 ≈ 字段 0.9295，C 给 0.9837）。
差得最大的 5 条全部是两侧长度不等的元件。

→ 结论：`ltr_identity` 是**可复算的**，但不是**唯一确定**的；残差来自"indel 是否
计入分母"的定义歧义，不是数据错误。**在基准里引用它时不要给到小数点后两位以上**，
判"两翼是否同源"用阈值 0.90 一类的粗档即可，不要拿 0.9927 与 0.9933 的差别做文章。

**LTR_retriever 版本**产物里没有，2026-11-23 在 WSL 环境实测：

```
$ grep -m1 'my $version' "$CONDA_PREFIX/share/LTR_retriever/LTR_retriever"

```

与产物里的 `strand_evidence` / `strand_conflict` 字段一致（这两个字段只出现在
LTR_retriever 的 `bin/make_gff3.pl`，EDTA tag v2.2.2 与 master v2.3.5 中 `git grep`
均为 0 命中）。

**这里有一个必须写进方法的复现风险：这是一对"跨代组合"。** EDTA v2.2.2 的 tag
commit 是 **2024-11-25**，LTR_retriever v3.0.8 是 **2026-11-09**，相差近两年；后者
距第一次运行（11-16）只有一周。也就是说，**别人按 EDTA v2.2.2 的文档装默认
LTR_retriever，未必能得到这六份结果**。任何复现都必须锁定这一对版本号，而不是
"装个 EDTA 2.2.2"。

**查版本的坑**：conda 装的 `LTR_retriever` 是 100 字节的 bash 包装脚本
（`perl $CONDA_PREFIX/share/LTR_retriever/${NAME} $@`），直接 grep
`$(command -v LTR_retriever)` 得到空结果——2026-11-23 实测如此。必须指向
`$CONDA_PREFIX/share/` 下的真实 Perl 主程序。这个坑也影响了 `run_bench_rice.sh`
的 `get_ver()`：首版只 grep `command -v` 给出的路径，对 LTR_retriever 永远返回
`unknown`；现已改为"先 grep 包装脚本，取不到就顺着 `perl <path>` 找到主程序"，
并用本地伪造的同构包装脚本验证通过。

六份运行的 `##date` 集中在 11-16 17:00 至 11-17 13:40（约 20 小时），加上 EDTA
版本逐文件确认、LTR_retriever 版本由环境确认，**"六份数据同一管线"这个前提现在
成立**——此前它只是推断。

> 可复现性提醒：`RUN_INFO.txt` 只记了参数、输入与路径，没有记版本。这是下一个
> 要补的字段——版本缺失时，"六份数据可比"这个前提无法证明。
>
> 已在 `run_bench_rice.sh` 补 `edta_ver` / `ltrr_ver` 两行（用
> `sed -n 's/.*my \$version *= *"\([^"]*\)".*/\1/p'` 从脚本自身读版本号），
> 此后每次运行自动留档。**六份历史数据仍需手工补这一次**。

## 六、复现

```bash
python TE_case/verify_ltr_structure.py \
  --gff rice/edta_out_multi/Oryza_sativa.Chr1_Chr12.fa.mod.EDTA.intact.gff3 \
  --fasta rice/Oryza_sativa.Chr1.fa rice/Oryza_sativa.Chr12.fa
```
