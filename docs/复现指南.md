# 复现指南

> 主线产物（六张台账、六数据集对比、四份检查报告）**一条命令、约 80 秒、12/12 逐字节一致**，
> 2026-11-24 实测。模块 2（Araport11 对比与交付包）另需外部注释，目前不能直接复跑，
> 原因写在第六节。重跑 EDTA 本体在第七节。

---

## 一、三种复现，成本差两个数量级

| 层级 | 复现什么 | 需要什么 | 实测耗时 |
|---|---|---|---|
| **L0 跑检查** | 十三项检查的文字报告 | 只有本仓库 | < 1 秒 |
| **L1 重建产物** | 六张台账 + 六数据集表 + 四份 JSON | Python + 基因组 FASTA | **77 秒** |
| **L2 重跑注释** | 从原始基因组跑 EDTA 出注释 | WSL + conda 环境 `edta` | 47–124 分钟/份 |

L1 是"验证结论"的层级：报告里每个数字都能从入库的 EDTA 输出重新算出来。
L2 是"验证注释"的层级：换一台机器重跑 EDTA，结果不会逐字节相同（工具内部有并行与
浮点顺序），只能比统计量。日常核对用 L1，L2 只在换环境或换物种时做。

## 二、序列从哪来

仓库不入库 FASTA（70 MB，且可重新下载）。`.gitignore` 已忽略，需要时按此表取回：

| 文件 | 长度 | 来源与处理 |
|---|---:|---|
| `ref/TAIR10.Chr1.fa` | 30,427,671 bp | Ensembl Plants **release-57**，`Arabidopsis_thaliana.TAIR10.dna.chromosome.1` |
| `rice/Oryza_sativa.Chr1.fa` | 43,270,923 bp | 同版本 `Oryza_sativa.IRGSP-1.0.dna.chromosome.1`，`tr -d '\r'` 清行尾，seqid 改为 `OsChr1` |
| `rice/Oryza_sativa.Chr12.fa` | 27,531,856 bp | 同上，`chromosome.12`，seqid 改为 `OsChr12` |
| `araport11_TE.gff3` | 9.2 M | Araport11 官方 TE 注释（仅模块 2 需要） |
| `ref/msu/osa1_r7.asm.repeat_masked.gff3.gz` | 7.5 M | MSU/UGA RGAP7（服务器慢，用 `curl -C -` 续传） |

**seqid 为什么要改**：EDTA 的产物流水线按输入 FASTA 的 seqid 命名，而 MSU 用 `Chr1`/`Chr12`。
改成 `OsChr1` 后，`link_msu.py` 有一条内建映射（去 `Os` 前缀）能对上；不改则台账全空。
两个 FASTA 合并即 Chr1+Chr12（70,802,779 bp，md5 `05b9072127587f084344991013ff3758`）：

```bash
cat rice/Oryza_sativa.Chr1.fa rice/Oryza_sativa.Chr12.fa > rice/Oryza_sativa.Chr1_Chr12.fa
```

## 四、分步命令（脚本里就是这几条）

输入统一为 `rice/edta_out_multi/Oryza_sativa.Chr1_Chr12.fa.mod.EDTA.intact.gff3`（420 LTR + 1,824 TIR）。

| 产物 | 行数 | 命令 | 耗时 |
|---|---:|---|---:|
| `ltr_structure.tsv` | 420 | `verify_ltr_structure.py --gff … --fasta Chr1.fa Chr12.fa --tsv` | **64 s** |
| `ltr_msu_ledger.tsv` | 420 | `link_msu.py --gff … --msu osa1_r7…gz --kind ltr --tsv` | 4 s |
| `ltr_abc.tsv` | 420 | `grade_ltr_abc.py --structure … --ledger … --tsv` | <1 s |
| `tir_structure.tsv` | 1,824 | `verify_tir_structure.py --gff … --fasta … --tsv` | <1 s |
| `tir_msu_ledger.tsv` | 62 | `link_msu.py --kind tir --anchor-tsv … --tier 强,中 --tsv` | <1 s |
| `tir_family.tsv` | 62 | `tir_family_cluster.py --gff … --ledger … --tsv` | <1 s |
| `bench_six.tsv` | 6 | `bench_multi.py "chr1=…" … --tsv` | <1 s |

```bash
PY=python   # WSL 里用 python3

$PY TE_case/verify_ltr_structure.py \
    --gff rice/edta_out_multi/Oryza_sativa.Chr1_Chr12.fa.mod.EDTA.intact.gff3 \
    --fasta rice/Oryza_sativa.Chr1.fa rice/Oryza_sativa.Chr12.fa \
    --tsv _repro/ltr_structure.tsv

$PY TE_case/link_msu.py \
    --gff rice/edta_out_multi/Oryza_sativa.Chr1_Chr12.fa.mod.EDTA.intact.gff3 \
    --msu ref/msu/osa1_r7.asm.repeat_masked.gff3.gz --kind ltr \
    --tsv _repro/ltr_msu_ledger.tsv
```

**为什么 `verify_ltr_structure` 要 64 秒**：它逐元件在 70 Mb 序列里取 LTR 两臂、比 motif、
算 TSD，420 条×三项。其余脚本只读 gff/tsv，全部亚秒级——所以总耗时几乎等于它一项。

四份 JSON 的命令在 `reproduce.sh --with-reports` 里；预飞那份需要 3 Mb 序列，仓库不含，
按 `run_bench_rice.sh` 的 PREFLIGHT 规则重建即可（取 Chr1 前 3,000,000 bp，换行 60）：

```bash
{ echo ">Oryza_sativa.Chr1.pre3000000"
  awk 'NR>1' rice/Oryza_sativa.Chr1.fa | tr -d '\n' | cut -c1-3000000 | fold -w 60; } \
  > _repro/pre3000000.fa
```

## 五、四份 JSON 在 2026-11-24 重建过一次

重建前它们只有 13 个键，是 C7–C13 加入之前生成的；而 `docs/维护记录.md` 写的是
"四次运行的十三项检查原始结果"——文件与文档不一致。重建后：

- 四份各补上 `C7…C13` 与 `note_total` 共 8 个键；
- 原有的 13 个键**取值一个都没变**，唯一例外是 `rice/preflight_report.json` 的
  `severe_total` 2 → 0：旧值是"未定超家族缺失也算严重项"的旧口径，现行判据按分层处理
  （`LTR/unknown` 不进严重项）。`TE_case/bench_six.tsv` 里 rice_pre 的 `severe` 一直是 0，
  说明台账早就是新口径，只有这份 JSON 没跟着重跑。

这类"文件与文档各说一套"的偏差，正是本工具在别处反复抓的东西，所以这里也记一笔。

## 六、模块 2：目前不能直接复跑

`compare_araport11.py` / `candidates_novel.py` / `make_publication_tables.py` /
`build_delivery_package.py` / `make_union_softmask.py` 都硬编码了本机的 WSL 路径：

```python
ED_GFF  = "//wsl.localhost/Ubuntu-26.04/home/sean/edta_run/chr1.fa.mod.EDTA.TEanno.gff3"
```

换一台机器这些路径不存在，脚本会直接报错。此外它们还依赖两样不在库里的东西：

`delivery/*`）当前只能"看"，不能"重算"。

需要时有两种做法：把五个常量改成环境变量（约十行），或者把 `chr1.fa.mod` 与
Araport11 注释补进 L0 下载清单。前者不改数据、只改入口，建议优先。

## 七、重跑 EDTA 本体（L2）

```bash
# 在 WSL 的终端里执行，不要在 Windows 侧跑
bash run_bench_rice.sh                      # 水稻 Chr1，默认 8 线程
THREADS=16 bash run_bench_rice.sh           # 指定线程
PREFLIGHT=1 bash run_bench_rice.sh          # 先截 3 Mb 试跑通链路
GENOME=... TAG=Chr1 SPECIES=others OUTDIR=... DEST=... bash run_bench_rice.sh   # 换基因组
```

脚本里锁了三件不能动的事，改之前先读脚本头部的注释：

1. **版本成对**：EDTA 2.2.2 + LTR_retriever 3.0.8。全部六份数据都在这一对版本下跑，
   升级会让新旧不可比。
2. **`.mod.mod` 双前缀缺陷**：EDTA 2.2.2 调 LTR_retriever 时没传 `-convert_seq_name 0`，
   后者又归一化一次，产物落到 `X.fa.mod.mod.*`，而 EDTA 按 `X.fa.mod.*` 找 → `LTR.raw.fa` 空。
   脚本用改名修复（纯 rename，不改内容），并在失败时自动重跑一次。
3. **不挂 curatedlib**：`USE_CURATED=1` 会把 EDTA 自带的 `rice7.0.1.liban.*` 挂上，
   那就不再是 de novo，结果不能与现有六份放同一张表。

耗时实测：TAIR10 Chr1 47 分钟；水稻 Chr1 73 分钟；Chr1+Chr12 124 分钟。

## 九、改了判据之后怎么用

1. `python test_te_check.py`（106 条）——先确认判据的边界没被改宽或改窄；
2. `bash reproduce.sh`——再确认六张台账变了没有；
3. 变了就回答一个问题：**这是判据该变，还是数据被改坏了**。

第 3 步没有捷径。本项目里 C3 的滑移口径、C10 的严格对位、C13 的 unknown 分层，三次改动
都让数字变化，三次都是判据错、数据没错——数字变化本身就是判据正确性的证据。
